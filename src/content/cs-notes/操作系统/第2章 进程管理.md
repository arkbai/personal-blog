# 一、进程与线程
## 进程
>多道程序的并发执行特征：间断性，不可再现性，为了控制程序并发行为引入<u>进程</u>
>程序-静态；进程-动态
### 1、进程的概念
> - 定义：程序对数据的一次运行过程 / 系统分配与调度资源的一个独立单位 / 正在动态执行的程序实例
> - 特征：动态性、并发性、独立性、异步性
> - 组成（进程映像）：PCB、程序段、数据段、栈
> - 基本状态：<u>就绪、运行、阻塞</u>、（创建、终止）

**进程管理功能**
1. 进程控制
2. 进程互斥与同步
3. 进程调度
4. 进程通信

 **进程和程序的区别**
1. 程序是静态的
2. 进程是独立运行的
3. 各进程异步，而程序顺序
4. 程序和进程是多对多的对应关系
### 2、进程控制块PCB
> 创建进程也就是创建pcb
1. 进程标识信息：进程标识符PID，用户标识符UID
2. 进程调度信息：进程状态、优先级
3. 进程现场信息：处理器状态【cpu上下文context】——通用寄存器、PC、PSW、栈指针等寄存器的值
4. 资源和内存信息：记录各类系统资源——各类文件资源、I/O资源、内存

## 线程
>线程是比进程更小的一个实体，一个进程可以有多个线程，共享进程的资源
><u>进程是资源分配的基本单位，线程是处理器调度的基本单位</u>
> - 作用：减小系统开销，提高并发程度
> - 组成：线程ID，寄存器，用户栈，内核栈，私有存储，线程控制块TCB

### 2、线程的实现
1. 用户级线程ULT：使用用户应用程序中自定义的线程库管理（早期Unix）
	- 优点：不需要切换到内核态，效率高；与操作系统无关，可移植性
	- 缺点：一个用户级线程阻塞后整个进程都会阻塞，并发度不高
2. 内核级线程KLT：可由操作系统管理，每个内核级线程维护一个线程控制块TCB
	- 优点：并行程度高，阻塞处理更灵活，内核可采用多核处理器提升效率
	- 缺点：需要用户态切换到内核态；系统开销大

3. **多线程模型**：令用户级线程--内核级线程进行对应
	一对一，多对一，多对多⬇

# 二、进程控制
>用**原语**实现
>PCB的进程状态（state）是进程控制的关键
### 原语
> **原语**具有原子性，不允许中断，通过2条特权指令【关中断指令，开中断指令】来实现

1. 进程创建——**创建原语**
	（*用户登录，作业调度，提供服务，应用请求* ）
	- 申请PCB / 为新进程分配资源，初始化PCB / 把PCB插入就绪队列（创建->就绪）
2. 进程终止——**撤销原语**
	（*正常结束exit，异常结束，用户关闭* ）
	- 从PCB集合中找到对应PCB / 剥夺CPU，终止其子进程，释放资源 / 删除PCB
3. 进程阻塞——**阻塞原语**
	（*等待系统分配资源或者等待其他进程* ）
	- 停止运行 / 保存现场信息到PCB中 / 运行->阻塞
4. 进程唤醒——**唤醒原语**
	（*等待的事件发生* ）
	- 从PCB集合中找到对应PCB / 把PCB移出阻塞队列（阻塞->就绪）
5. 进程切换——**切换原语**
	（*时间片结束，高优先级进程插队，当前进程主动阻塞/终止* ）
	- 将<u>运行环境</u>信息存入PCB / PCB移入对应的队列以后，执行另一个进程 / 根据PCB恢复新进程所需的<u>运行环境</u>
> 运行环境：即进程的上下文context

### Linux进程控制
进程创建：fork（）——如果不终止，第二次将会创建子进程：进程终止：exit（）
1. 在父进程中，fork()返回新创建子进程的进程ID。    
2. 在子进程中，fork()返回0。
3. 如果出现错误，fork()返回一个负值。

>fork()函数的执行过程
> 
> 1. **申请PID**：为新进程申请一个唯一的进程ID。
> 2. **申请PCB结构**：为新进程申请一个进程控制块（PCB）。
> 3. **复制父进程的PCB**：将父进程的PCB复制到新进程中。
> 4. **设置子进程的运行状态**：将子进程的运行状态设置为不可执行的。
> 5. **清零和保留某些属性**：将子进程中的某些属性清零，某些保留，某些修改。
> 6. **复制父进程的页**：使用写时拷贝技术，初始阶段父子进程共享所有的数据，当任意一个进程试图修改数据时，内核才会将要修改的数据所在的区域拷贝一份。

# 三、进程互斥与同步
>- 进程的**异步性**：并发执行的进程以各自独立的、不可预知的速度向前推进
>- **进程同步**（直接制约关系）：由于读/写进程并发执行，执行先后顺序不确定（异步），为了处理异步性【令进程按合适的顺序执行--先写后读】，需要实现进程同步
>- **进程互斥**（间接制约关系）：当一个进程正在使用临界资源时，其他试图访问的进程需要等待，当该进程退出时，其他进程才能访问临界区

## 1、进程互斥的基本概念
- 临界资源：一次只有一个进程使用的资源
	eg:打印机/多个进程共享的变量或数据结构；如果对临界资源没有设置进程互斥，如两个打印机一起工作，打印内容会混在一起
	1. 进入区
	2. 临界区
	3. 退出区
	4. 剩余区 
	```c
	do{
		entry section;
		critical section;	//访问临界资源的代码段->临界区
		exit section;
		remainder section;
	}while(true)
	```
 - 互斥访问的原则：
	 1. 空闲让进：临界区空闲时，允许请求
	 2. 忙则等待
	 3. 有限等待：避免进程无限等待
	 4. 让权等待：进程无法进入临界区时，应当主动放弃cpu转为阻塞态，<u>避免忙等待</u>（不停申请临界资源）

## 2、实现进程互斥的方法

### 软件方法
 1. **单标志法**：每个进程访问完临界区后，把权限交给下一个进程
	- 两个进程只能交替执行——违反‘空闲让进’
	 `while(turn!=0){... turn=1;}`
		`while(turn!=1){... turn=0;}`

 2. **双标志先检查法**：设置flag\[2]，标记各进程进入临界区的意愿
	- 检查与上锁不是原子的，在上锁前可能发生进程切换——违反'忙则等待'
	```c
	P0:
		while(flag[1]); 	//检查，若P1正在访问，则循环等待
		flag[0]=true;		//上锁
		critical section	//临界区代码
		flag[0]=false		//释放锁
		remainder section
			
	P1:
		while(flag[0]);
		flag[1]=true;
		critical section
		flag[1]=false;
		remainder section
	```

 1. **双标志后检查法**：先上锁后检查
	 - 如果刚好两个进程都上锁，就会导致无限等待——违背了‘空闲让进’和‘有限等待’
	```c
	P0:
		flag[0]=true;		//上锁
		while(flag[1]); 	//检查
		critical section
		flag[0]=false
		remainder section
	```
2. **Peterson算法**：结合单，双标志法，“主动争取，主动谦让”
	- 使用while循环等待另一个进程访问完毕，如果另一个进程一直访问失败，则会产生忙等待——违反’让权等待’
	```c
	bool interested[2];
	int turn;						//两个进程都可以修改的全局变量
	//P0
	void process0()
	{
		interested[0] = true;		//表明p0想访问临界区
		int turn = 1;				//表示可以谦让给1进入
		while(turn==1 && interested[1]); 
		//若P1有意愿访问临界区，则谦让给P1，若P1访问完毕，则阻塞结束
		critical section				//临界区
		interested[0] = false;
	}
	//P1	
	void process1()
	{
		interested[1] = true;		//表明p1想访问临界区
		int turn = 0;				//表示可以谦让给0进入
		while(turn==0 && interested[0]); 
		critical section			
		interested[1] = false;
	}
	```
> <u>先谦让的会先执行</u>：两者都谦让，后谦让的一方最后修改了turn值，然后进入忙等，此时另一个进程的while条件被修改，结束等待

### 硬件方法
1. **中断屏蔽**：用特权指令（关中断，开中断）实现
	- 关中断只影响当前cpu，不适用多处理机系统
	- 只适用于操作系统内核进程，不适合给用户使用
2. **TestAndSet**（TS/TSL指令）
	- TSL指令由硬件实现，是原子操作，令‘上锁’与‘检查’的过程同时完成
	- 使用全局变量lock，适合多处理机系统
	- 使用while循环，会出现忙等待——违反‘让权等待’
	```c
	bool lock;			//全局变量lock，表示当前临界区是否被加锁
	
	//TSL指令：读取并返回当前lock值，然后将其修改为true
	bool TestAndSet (bool *lock){
		bool old;			
		old=*lock;		//old用来存放 lock原来的值
		*lock=true;		//无论之前是否已加锁，都将lock设为true
		return old;		//返回 lock原来的值
	}
	
	//使用TSL指令实现互斥
	//进程P0
	while(TestAndSet(&lock));	//"上锁"并“检查”
	//若old=false则结束等待并上锁，若old=true说明临界区占用，循环等待
	critical section;
	lock = false;	//“解锁”
	···
	
	```

1. **Swap指令**（Exchange指令）
	- swap指令由硬件实现
	- swap指令与TS指令本质上一样，一个用原子操作合并上锁与检查，一个用交换值的方式合并上锁与检查

	```c
	bool lock;			//全局变量lock，表示当前临界区是否被加锁
			
	//Swap指令：交换变量
	Swap(bool *a,bool *b){
		bool temp; temp= *a; *a=*b; *b=temp;
	}
	
	//Swap指令实现互斥
	bool old=true;		//每次尝试访问临界区时，将lock初始化为ture
	while (old==true)
		Swap (&lock,&old);	
		//若old=false则结束等待并上锁，若old=ture则说明全局lock=true，循环等待
	critical section;
	lock = false;
	···
	```

> 硬件指令方法实现进程互斥（TS、swap）的优点：1.实现简单 2.多处理机 3.多个临界区可以设置多个lock变量来实现

## 3、锁机制
- **互斥锁**：进程进入临界区获得锁，退出时释放锁
	- 其他进程可能循环调用获得锁的函数，导致<u>忙等待</u>⤵自旋锁
	- 硬件实现acquire和release函数
	```
	获得锁：
	acquire()
		while(!available);	//忙等待
		available=false;
		}
	释放锁:
	release(){
		available=ture
	}
	```

- **自旋锁**：需要连续循环忙等待的互斥锁【忙等--TSL、Swap、单标志法】
	- 自旋锁通常用于多处理器系统，一个线程可以只在一个cpu上自旋等待，而不影响其他cpu
	- 进程在等待锁期间没有进行上下文切换，等待代价开销较小
## 4、信号量机制
>信号量 Semaphore
>- 进入区的‘检查’和‘上锁’操作不能一次完成；以上所有方法都不能实现<u>让权等待</u>
>- 用户进程可以使用操作系统的一对**原语**P、V来对信号量操作
>	P--wait（）申请资源
>	V--signal（）释放资源
<img src="images/QQ_1787730167617.png" width="623">
- **整型信号量**：整型变量S来表示当前可用资源的数量
	- 缺点是进程没有资源时会<u>忙等待</u>
		```c
		Int S = 1;				//初始化整型信号量s
		Void wait (int S) {		//wait原语，相当于“进入区”
			while (S <= 0);		//如果资源数不够，就一直循环等待
			S=S-1;				//如果资源数够，则占用一个资源
		void signal(int S){		//signal原语，相当于"退出区"
			S=S+1;				//释放资源
			
		//P0进程
		wait(S);
		critical section;
		signal(S);
		```
- **记录型信号量**：semaphore{value，L}，用value表示可以资源数量，队列L存储等待中的进程
	- 通过阻塞机制（替换while循环访问），实现了‘让权等待’
	- value=-m表示有m个进程等待
		```c
		/*记录型信号量的定义*/
		typedef struct {
			int value;				//剩余资源数
			struct process *L;		//等待队列
		}semaphore;
		/*某进程需要使用资源时，通过wait原语申请*/
		void wait (semaphore S){
			S.value--;
			if (S.value <0){			//当前没有空闲资源
				block (S.L);		
				//block原语，运行->阻塞，放弃cpu，并把当前进程加入等待队列L
		}
		/*进程使用完资源后，通过signal原语释放*/
		void signal(semaphore S){
			S.value++;
			if (S.value <= 0){		//当前有等待中的进程
				wakeup(S.L);			
				//wakeup原语，阻塞->就绪，从等待队列L中移出一个进程来运行
		}
		```

### (2) 读者-写者问题
> 系统中存在两组并发进程读者和写者共享一个文件，多个读者同时读取文件不会导致数据不一致，但是写者+其他进程同时访问文件会导致数据不一致
> 1. 允许多个读者同时执行read
> 2. 任意时刻只能允许一个写着执行write
> 3. 写者开始write之前需要等待其他进程都退出
> 4. 写者完成write之前不允许其他进程（读者/写者）访问文件
> - 互斥：读者--写者；写者--写者
> - 同步：无

# 四、进程调度
## 1、cpu调度的层次
>cpu调度：系统按照某种算法，选择某些作业或进程，把cpu分配给其运行
>越低级的调度频率越高
1. 高级调度（作业调度）：从作业队列中选择作业<u>调入内存</u>，并为其创建进程；创建->就绪
> 系统可以同时处理多道作业但是只能运行单个进程，这时需同时考虑作业调度与进程调度
2. 中级调度（内存调度）：将进程先挂起<u>调到外存</u>，组成<u>挂起队列</u>；条件满足时，将进程调回内存；因此可增加两种进程状态——就绪挂起 / 阻塞挂起⬇
	<img src="images/QQ_1787196081758.png" width="643">
> PCB常驻内存，挂起操作将进程映像中的数据段、程序段调到外存中
3. 低级调度（**进程调度**）：最基本的调度，给进程分配cpu，就绪->运行

## 2、进程调度的概念
> 狭义进程调度 vs 进程切换：狭义的进程调度——分配cpu资源给进程；进程切换——保存现在进程状态&恢复另一个进程状态
### (1) 进程调度任务&调度程序&闲逛进程
- 调度任务：1. 保存现场 2. 根据调度算法选取待运行进程 3. 分配cpu
- 调度器：实现调度算法，处理对象为进程/内核级线程；组成：1. 排队器 2. 分派器 3. 上下文切换器
- 闲逛进程idle：优先级最低，占一个指令周期，没有就绪进程时就执行《让cpu不能闲着》
### (2) 进程调度的时机
- **需要**进行调度与切换的情况
	- 进程**主动**放弃cpu：
		1. 父进程运行时，创建子进程
		2. 进程正常结束/异常终止
		3. 进程运行->阻塞（I/O请求、信号量）
		> 发起 I/O 请求 ≠ I/O 中断
		
	- 进程**被动**放弃cpu
		1. 抢占：时间片用完 / 更高优先级到达
		2. I/O设备就绪，发出I/O中断
			【当原先等待I/O的进程从阻塞->就绪时要判断运行该等到I/O的进程，还是继续运行原来的进程】
----------

- **不能**进行调度与切换的情况
	1. 处理中断的过程中，属于内核工作，cpu转向执行中断处理程序，逻辑上不属于用户进程
	2. 原子操作
	3. 进程在<u>内核程序临界区</u>，访问如就绪队列等内核数据
	> 临界资源：一个时间段内只允许一个进程使用，各进程需互斥访问
	
	
	<img src="images/Pasted%20image%2020260103171735.png" width="573">
### (3) 进程调度方式
1. 非抢占方式（批处理）：除非进程阻塞或终止，否则不会被打断
2. 抢占方式（分时、实时）
> 优先短作业/高优先级，不一定是抢占的

## 3、进程调度算法
> 批处理：FCFS、SJF、HRRN；交互式：RR，优先级，多级反馈队列
1. **先来先服务调度算法** FCFS
	- 实现简单，效率低，利于长作业，非抢占
2. **短作业优先** SJF
	- 对短作业有利，平均等待时间较短，会出现饥饿现象，非抢占
	- 最短剩余时间调度算法：根据剩余时间<u>抢占式</u>分配进程
3. **高响应比优先** HRRN
	- 响应比 = (等待时间+要求执行时间）/ 要求执行时间
	- 平衡了两者优缺点⬇
		等待时间相同时，要求执行时间短的优先--SJF
		要求服务时间相同时，等待时间长的优先--FCFS
	- <u>避免了饥饿</u>；每次都要计算响应比，增加系统开销，非抢占
	> 饥饿现象：一些作业长期得不到服务
4. **优先级**
	- **静态优先级**：优先级始终不变；实现简单，系统开销小，低优先进程可能出现饥饿
	- **动态优先级**：等待时间过长、频繁I/O操作--提高优先级；运行时间过长--降低优先级；灵活
	- 抢占/非抢占
> 优先级设置的原则：
> 	1. 系统进程>用户进程
> 	2. 前台进程>后台进程
> 	3. I/O进程>计算型进程
5. **时间片轮转** RR
	- 轮流让就绪队列中的进程执行一个时间片，当前时间片用完了就令进程到队列中重新排队，未用完时间片则直接运行下一个
	- 时间片过长会增大响应时间 / 时间片过短会导致切换过于频繁
	- 公平，响应快，进程切换存在开销，<u>用户友好</u>，抢占
6. **多级队列**
	<img src="images/QQ_1787549174897.png" width="399">
	- 设置多级就绪队列，每个队列对应一类进程（系统进程-交互式进程-批处理进程），各队列可采用不同的调度策略，eg:交互式-RR-提高响应速度，批处理-FCFS-提高吞吐量
	- 抢占，灵活处理不同类型的进程
7. **多级反馈队列**：抢占式
	<img src="images/Pasted%20image%2020260103175847.png" width="420">
	- 时间片+优先级+多级队列；
		1. 多级队列：下一级队列的时间片大小通常为上一级的两倍
		2. 时间片：新进程到达时先进入第1级队列，按FCFS原则排队等待被分配时间片；若用完时间片进程还未结束，则进程进入下一级队列队尾（如果已经是在最下级的队列，则重新放回该队列队尾）
		3. 优先级：优先执行高优先级队列，只有第k级队列为空时，才会为k+1级队头的进程分配时间片
	- 优点：交互型用户-进程较短且频繁I/O，在高优先队列中快速完成；批处理-短作业在高级队列快速执行，长作业会先进入高优先队列处理，再降低优先级，饥饿现象较少
## 4、调度算法的评价指标
- cpu利用率 = cpu工作时间 / 总时间
- 系统吞吐量 = 作业数量 / 总时间
- **周转时间** = 作业完成时间 - 作业提交时间
- 平均周转时间 = 各个作业的周转时间和 / 作业数量
- 带权周转时间 = 周转时间 / 实际执行时间
- 等待时间：作业等待cpu时间之和【等待I/O不算】
- 响应时间：首次产生响应的时间 - 提交时间

## 5、多处理机调度
>单处理机调度：只需决定哪个就绪进程优先进入cpu
>多处理机调度：还需决定进入哪个cpu
1. 分类：
	1. 非对称多处理机AMP：主从架构，主cpu负责调度决策，其余cpu只执行任务
	2. 对称多处理机SMP：所有cpu都参与调度
2. 目标：
	- 负载均衡：每个cpu同等忙碌
	- 处理器亲和性：尽量使一个进程在同一个cpu上运行（充分利用cpu缓存cache）
	- 负载平衡和处理器亲和性会相互影响
3. 方案：
	1. 公共就绪队列：所有cpu共享一个就绪进程队列，每个cpu运行调度程序来从队列中选择进程运行——负载均衡好，需要提高亲和性⬇
		- 软亲和：进程调度程序
		- 硬亲和：用户进程通过系统调用控制分配的cpu
	2. 私有就绪队列：每个cpu都有一个就绪队列，从自己的队列中选择程序运行——亲和性好，需要平衡负载⬇
		- 推迁移push策略：负载高的推给别的cpu
		- 拉迁移pull策略：负载低的拉进程

# 六、进程死锁
>死锁：循环等待

### 1、死锁的概念
1. 死锁与饥饿

|     | 共同点      | 区别                                 |
| --- | -------- | ---------------------------------- |
| 死锁  | 进程无法顺利推进 | 循环等待对方手中资源，死锁现象一定有两个以上进程阻塞         |
| 饥饿  | -        | 可能只有一个进程由于长期得不到资源而阻塞，或得不到cpu而处于就绪态 |
| 死循环 | -        | 代码逻辑错误，可能在运行态                      |
2. 死锁发生的时机
	1. 空间上-对系统资源的竞争（互斥资源分配不合理）
	2. 时间上-进程推进的顺序不合理
	3. 信号量使用不当（PV顺序不对，可以将信号量也看成一种资源）
3. 死锁的必要条件（都需满足才能发生死锁）
	1. 互斥条件：资源同时只能由一个进程使用【独占/临界/互斥】
	2. 不可剥夺条件：进程不能被其他进程抢占
	3. 请求并保存条件：进程持有资源时又提出了新的资源请求
	4. 循环等待条件：存在循环等待关系

### 2、死锁的处理策略
1. 静态-预防死锁：提前添加限制，破坏死锁的必要条件
	- SPOOLing技术：破坏<u>互斥条件</u>，将独占设备逻辑上变为共享设备
> <img src="images/QQ_1787991653374.png" width="541">

2. 动态-避免死锁：每次分配资源时动态判断是否会引起死锁
	- 银行家算法

3. 检测和解除死锁
	1. 资源分配图（P1-进程结点 R1-资源结点）
		<img src="images/Pasted%20image%2020260104211947.png" width="300">
		eg:⤴R1出度=3，资源分配完；R2出度=1，剩余资源1，可分配给P1的请求，因此P1未阻塞，删去所有边，此时R1有剩余资源2，可分配给P2的请求

	2. **死锁检测算法**
		- **死锁定理**：消去所有的“<u>既不阻塞又不独立</u>”的进程节点的边，如果所有节点都变成独立的，那么称该图可完全简化，此时没有死锁发生
		
	3. 死锁的解除
		- 资源剥夺法：挂起部分死锁进程，抢占并分配给其他死锁进程
		- 撤销进程法：终止部分死锁进程
		- 进程回退法

### 银行家算法
> 在进程提出资源申请时，先预判此次分配是否会导致系统进入不安全状态，如果会，则阻塞该进程
- 安全序列：系统按顺序分配资源，每个进程都顺利完成并释放资源
- 不安全状态：不存在一个安全序列——不一定死锁
- 安全状态：存在——一定不会死锁
- 安全序列的计算（手算）![](images/Pasted%20image%2020260104211236.png)
	

-------------
算法中的变量
- 最大需求矩阵Max\[i,j]
- 分配矩阵Allocation\[i,j]
- 需求矩阵Need\[i,j]
- Need<sub>i,j</sub> = Max<sub>i,j</sub> - Alllocation<sub>i,j</sub>
	<img src="images/QQ_1787992672095.png" width="339">
- 可用资源向量Available\[j]
- 资源请求向量Request<sub>i</sub> \[j]：表示对进程Pi的资源申请

算法过程
1. 合法性检查
	`Request i[j] <= Need[i,j]`
2. 资源可用性检查
	`Request i[j] <= Available[i,j]`
3. 试探性分配
	`Available[j] -= R[j] //总资源减少`
	`Allocation[i,j] += R[j] //进程i获得资源`
	`Need[i,j] -= R[j] //更新需求资源量`
4. 安全性检查：若不安全，则撤销3

- 安全性算法
> 检查当前的<u>剩余可用资源是否能满足某个进程的最大需求</u>，如果可以，就把该进程加入安全序列，并把该进程持有的资源全部回收；不断重复上述过程，看最终是否能让所有进程都加入安全序列。

1. 设置向量
	`Work = Available //测试` 
	`Finish[i]=false //标注进程是否顺利完成`
2. 查找安全进程
	`if Finish[i]=false && Need[i]<=W`
3. 执行进程并释放资源
	`work+=Allocation[i], Finish[i]=True`
4. 判断完成向量
	`if 所有进程 Finish[i]=True`
